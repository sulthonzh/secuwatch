## Findings

### 🔴 MEDIUM: Missing Path Traversal Validation in Public Assets Endpoint

**Location:** `packages/twenty-server/src/engine/core-modules/file/controllers/file.controller.ts:49`

**Vulnerability:**
```typescript
@Get('public-assets/:workspaceId/:applicationId/*path')
@UseGuards(PublicEndpointGuard, NoPermissionGuard)
async getPublicAssets(@Res() res: Response, @Req() req: Request, ...) {
  const filepath = join(...req.params.path);  // NO VALIDATION
  ...
}
```

**Attack Vector:**
- Route uses wildcard `*path` which captures everything after `:applicationId`
- URL: `/public-assets/workspace123/app456/../../sensitive.txt`
- `req.params.path` = `['..', '..', 'sensitive.txt']`
- `join(...req.params.path)` = `'../../sensitive.txt'`

**Why This Is Vulnerable:**
1. Controller receives untrusted user input (`req.params.path`)
2. Joins path segments **without validation**
3. Passes unvalidated `filepath` to database query FIRST
4. Only THEN does storage layer validate with `assertStoragePathIsSafe`

**Impact:**
- Database query runs with malicious filepath before storage validation
- If malicious file paths exist in database (from other endpoints), they could be accessed
- Allows attackers to enumerate files across workspaces/applications
- Public assets are accessible without authentication
- Defense-in-depth issue - bypass possible if storage driver changes or validation is disabled

**Mitigations:**
- Storage layer (`assertStoragePathIsSafe`) does block `../` sequences
- Database query might fail for non-existent paths
- However, timing attacks could reveal file existence

**Proposed Fix:**
Add validation at controller level before database query:
```typescript
import { assertStoragePathIsSafe } from 'src/engine/core-modules/file-storage/utils/assert-storage-path-is-safe.util';

// Validate filepath before database query
assertStoragePathIsSafe(filepath);
```

## Analysis

Twenty has good security practices overall:
- Storage layer has comprehensive path validation (`assertStoragePathIsSafe`)
- SNS webhook URL validation prevents SSRF
- Uses NestJS guards for authentication/authorization
- No obvious XSS or SQL injection vulnerabilities found

However, this finding reveals a defense-in-depth issue where validation happens too deep in the stack. Security best practice is to validate at the entry point (controller) rather than relying on downstream services.

The lack of input validation at the controller level means:
- Debugging becomes harder (errors surface at storage layer instead of controller)
- Security can be bypassed if storage implementation changes
- Attackers can probe the database even if file read fails
- Timing attacks could reveal sensitive information

## Lessons Learned

1. **Validate early, validate often** - Input should be validated at the entry point, not just at storage/service layers
2. **Defense-in-depth matters** - Even if one layer validates, other layers shouldn't blindly trust input
3. **Database queries with user input** - Always validate before querying database, not just before file operations
4. **Public endpoints need extra scrutiny** - The `@UseGuards(PublicEndpointGuard, NoPermissionGuard)` annotation makes this particularly sensitive

## Recommendation

The maintainers should:
1. Accept and implement the fix at controller level
2. Consider adding linter rules or static analysis to catch unvalidated path joins
3. Audit other routes with wildcard parameters for similar issues
4. Add integration tests for path traversal attempts
